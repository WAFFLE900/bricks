# Human-Needed Decisions

Open decisions that require a human/team call. Each is a working assumption the
architect adopted to keep progressing; confirm or override.

## Design fork: Realtime transport / provider
- Decision (working assumption): WebSocket endpoint inside FastAPI (Starlette) + y-py.
- Needs human: yes.
- Tradeoff: The choice is correct FOR THE CURRENT TOPOLOGY (one uvicorn process, no workers/broker) and only for it. In-process Y.Doc authority breaks the moment you scale out — if you ever add uvicorn --workers, gunicorn, or a second Render node, two connections to the same textbox can land on different processes with divergent docs and F1/F4 fail. The DB snapshot layer protects durability across restart/spindown but does NOT provide cross-process fan-out. If horizontal scale is on your roadmap, or if you'd rather not build+own the CRDT sync/durability glue at all, switch to T-node (Hocuspocus) or T-managed now instead — the revision keeps the client on the standard y-websocket protocol precisely so that migration stays a server-only swap. Flag me if multi-node scaling is actually planned.

## Debounced CRDT flush has no known/single actor for _notify_new_mentions attribution
- Decision: Option 2 (revise-feature: attribute at the authenticated per-update apply seam), synthesized as the winner — its per-connection burst-coalescing refinement is kept, and its ALT ledger sub-variant is adopted as the default emission mechanism. Option 1 is subsumed (same core, minus churn control and crash-window fix). Option 3 is explicitly rejected: its flush-time token->earliest-author tracing is strictly more machinery for attribution no better than the ledger's, and it adds a silent-drop coverage gap.
- Needs human: yes.
- Tradeoff: Two things need a human/team call before this can be built or merged. (1) PREREQUISITE NOT PRESENT: this branch has no realtime-collab implementation at all — no WS route is mounted (router.py mounts only REST routers), no CRDT library is a dependency (websockets appears only as a transitive uv.lock entry), no snapshot column exists, and no run_in_threadpool is used. All three options explicitly ride on a "sibling persistence fork" that introduces the room/session/Y.Doc/snapshot surface these hooks attach to. The attribution DESIGN is settled and sound, but it cannot be implemented or verified until that collab persistence layer lands, and its integration details (room lifecycle, ledger reset-on-flush, roster refresh, threadpool worker) depend on decisions in that fork not visible here. (2) EMISSION-TIMING CHOICE: I default to the ledger (drain-at-flush) because it closes the crash window where a notification outlives not-yet-durably-saved text. The simpler plain emit-at-ingest is defensible on parity grounds — REST's own PATCH+commit has a comparable window and no dedupe, and free-tier rooms are short-lived — but it leaves that window open. Team should confirm the ledger's modest per-room bookkeeping is worth closing it, and sign off on the accepted degradations: concurrent-merge mentions credited to a real-but-not-semantically-authoritative editor, and up-to-one-debounce-window delay before mention notifications fire.
